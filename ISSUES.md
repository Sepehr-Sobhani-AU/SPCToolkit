- ~~Deselecting anything after a lasso silently collapses the selection to the LOD subset.~~
  - **FIXED 2026-09-16** by the selection refactor (`DECISIONS.md` § 2026-09-16). The selection is now a boolean mask per branch over that branch's full-resolution cloud, so deselect is `mask &= ~inside` — an ordinary subtraction that cannot lose the widening. Nothing clears stored polygons any more, because nothing depends on them. Regression test: `unit_test/selection_edge_cases_test.py::test_deselecting_does_not_collapse_the_selection`.
  - **Original report (Open / bug):** `deselect_point_at` (`_point_picking.py`) and `_close_polygon_and_deselect` (`_polygon_selection.py`) both call `self._selection_polygons.clear()`. Once the stored polygons are gone, `get_selection_mask_for` / `picked_cloud_indices` lose the full-resolution re-test path and fall back to coordinate-matching the *rendered* picks only. So a lasso that would have handed a plugin 1,000,000 points hands it ~100,000 after the user Shift+Right-clicks one stray point. Nothing on screen changes — the highlight only ever drew the rendered picks — so the user has no way to notice. Net effect: "does the pipeline select LOD-hidden points?" currently answers *yes, unless you deselected anything*, which is not a rule anyone can hold in their head.
  - **↳ Suggestion:** store deselect polygons as **negative** polygons (polygon + mv + proj + viewport, same tuple) and subtract them in `retest_polygon_selection`, so widening survives any number of add/remove lassos and select/deselect stay symmetric. For single-point deselect, record the removed **coordinate** as an exclusion rather than dropping the polygons — it is one point, so the cost is trivial. Cheapest stopgap if the fix is deferred: surface the true full-resolution count (see the feedback item below) so the collapse is at least visible.

### Not issues — recorded so they are not "fixed" by mistake

- **Polygon selection includes LOD-hidden points, deliberately.** A lasso is an *area* gesture; the region exists independently of how many points were drawn. Returning only rendered points would make `Separate Selected Points` produce a subsample full of holes, with a different result at every zoom level. Storing the polygon + camera matrices makes the re-test exact and reproducible, which is what pipeline replay needs.
- **Single-point click does NOT widen, deliberately.** A click is an *identity* gesture naming one point; the pick tolerance absorbs mouse imprecision and is not a capture radius. Widening it would scale the points-per-click with the LOD factor, silently and with no feedback. The practical route to a specific LOD-hidden point is to zoom in until AUTO-LOD draws it — or, where the point is hidden for a semantic rather than a density reason, to promote it to a visible cluster first, as the line-extension window does with `pick_candidates`.
